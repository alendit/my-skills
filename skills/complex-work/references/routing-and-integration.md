# Conditional Routing And Integration

Read only the section activated by the unit being routed. These are coordinator
inputs and results; the linked leaf owns the detailed procedure.

## Cost-based delegation

Delegate when the user requests it, the selected leaf requires it, an established
execution-cost profile identifies a cheaper capable owner for suitable code or
evidence-producing work, or packages are genuinely independent. Keep prose-heavy
authorship with the primary unless explicitly delegated.

When material cost differences are supplied or observable, record the selected
cheaper capable owner/configuration and retain exhaustive mechanical work and
verbose evidence there. Include parent waiting, polling, and interpretation
cost when material; distinguish raw input, cache effects, and new context only
when telemetry permits. Do not invent prices or savings. The coordinator
consumes configuration rather than selecting a default model or team.

## Continuity across units

When routing SIL work, carry the caller-required continuity mode, selected
model/reasoning/execution configuration, safe accepted renewal boundary, and
replacement authority. Consume SIL's result without copying turnover records.

- On `renew-at-boundary`, preserve accepted inner packages and outer dependency
  decisions whose evidence remains valid. Renewal does not create a new outer
  unit or accept the whole existing unit.
- On `stop-and-rebaseline`, replan the affected unit and dependents from the
  last accepted boundary. SIL owns writer settlement and partial-work recovery.

## Terminology at handoffs

Resolve or consume [glossary state](../../clear-technical-writing/references/project-glossaries.md)
at establishment when relevant; pass `local-only`, `opt-out`, or selected source
and material dispositions to leaves. Carry only changed or still-material state
afterward. Refresh selected-source evidence only for affected term decisions;
absent glossary metadata does not block otherwise valid work.
Technical owners retain meaning; this transport does not authorize glossary
writes or new implementation mechanisms.

## Design-sensitive units

Carry the repository's [architecture guidance](../../add-architectural-guidances/references/guidance-contract.md).
For each changed responsibility, ask its leaf for the semantic owner, selected
physical source boundary, and cohesion reason. Semantic authority and physical
placement are separate; ordinary changes need this lightweight disposition,
not a whole-root topology inventory.

When decomposition is explicitly in scope or source/dependency/state/test
evidence qualifies a decomposition defect, route the affected unit through the
[architectural-scope authority](../../supervised-implementer-loop/references/architectural-scope-decision.md).
Consume activated scope, residual coverage, separate preservation/locality
evidence, and fixed-point eligibility. Several units touching one owner call
for checking its disposition; overlap or size alone does not activate the full
procedure. Before acceptance, integrate the leaf's baseline-to-result decision
where owner overlap applies. Replan if evidence invalidates the assumed owner.

## Update an installed skill

Use only when the authorized outcome includes an installed skill update.

1. Determine whether the selected distribution is standalone or plugin-based.
2. Resolve and inventory its source and installed location/cache; preserve the
   current source recoverably.
3. Follow that distribution's supported update flow using the applicable
   installer/plugin skill or repository instructions.
4. Read back the installed skills, reference closure, revision provenance, and
   resolved cache contents before reporting the update complete.
