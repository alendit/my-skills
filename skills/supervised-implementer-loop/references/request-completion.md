# Request Completion And Runtime Goals

Use this reference at work establishment, accepted edit/package/phase boundaries,
and before ending an implementation turn. The primary agent owns continuation
toward the user's requested outcome; a leaf owns only its assigned package.
Existing skills retain edit sequencing, acceptance, independent review, writer
settlement, and authorization. This reference supplies the stopping decision,
not another review phase or work ledger.

## Continue At The Correct Boundary

1. Identify the complete currently authorized outcome and its acceptance
   evidence. Reuse the existing package/behavioral goal record; distinguish the
   user's outcome from the current edit, delivery package, or Tock. Do not
   redefine the request around the amount of work already completed.
2. After an edit result, select its correction or the next admitted edit. After
   package acceptance, return control to the outer workflow if one exists; the
   primary selects the next authorized package, gate, or independent review.
   A leaf returning a result is not the primary ending the user-facing turn.
3. If an in-scope design or evidence question interrupts the sequence, resolve
   it at its owner and resume from the accepted boundary. Stop for user input
   only when the remaining decision or action genuinely needs new authority
   or missing information that safe in-scope work cannot supply.
4. When a delegated writer is running, use its progress envelope and completion
   events. Continue waiting through ordinary timeouts; do not replace useful
   work with repeated agent listings, goal reads, or reassurance requests.
5. Before a final implementation response, decide from the latest user intent:
   - **Complete:** the requested outcome has its required verified acceptance
     evidence, with no required work remaining. Report that evidence and stop.
   - **User-directed boundary:** the user requests a pause, handoff, explanation
     only, or a different task. Honor that boundary; settle any writer that
     must stop under its lifecycle rules. Do not resume implementation merely
     because an earlier objective remains incomplete.
   - **Concrete blocker:** name what prevents the next authorized step, the
     relevant evidence, and the exact input or external change needed. Exhaust
     safe in-scope alternatives; do not bypass a safety rejection or expand
     authority to keep moving.
   - **Otherwise:** continue the next safe, authorized step. An accepted edit,
     convenient checkpoint, amount of effort, or prepared handoff is not an
     independent reason to stop.

A useful stopping point makes partial work recoverable; it does not select the
time to end a larger request. Conversely, completion of the actually requested
bounded package does not authorize adjacent cleanup or another project phase.
A user-requested handoff may truthfully describe incomplete work without calling
the request's implementation outcome complete.

## Use Runtime Goals When Authorized

The behavioral goal record describes what must work and its evidence. A runtime
goal is a platform's persistent execution objective; its status is not acceptance
evidence. Keep these distinct and reference existing records rather than copying
their matrices into a second tracker.

For a long supervised request, offer a runtime goal once when that would help
persistence. Create one only when explicitly requested by the user or system
and supported by the current tool contract. A request to continue implementation
or reach fixed point is not, by itself, permission to create a runtime goal.
Do not block ordinary authorized work waiting for optional goal consent, and do
not create a goal merely to discuss or edit this guidance.

When authorized:

1. Inspect the current goal at establishment or recovery when its identity is
   unknown. Reuse the matching active objective; do not overwrite an unrelated
   unfinished goal or silently attach a new task to it.
2. Track the complete authorized outcome in one goal across its edits and
   packages, including required verification and independent acceptance. Add
   a token budget only when explicitly requested. Do not create a goal per edit.
3. On continuation, reconcile the latest request, current repository, accepted
   evidence, and writer state. Resume the first unmet obligation without replaying
   completed work. Read goal state only when it can affect this decision, not as
   an additional polling loop.
4. Mark complete only after the objective's acceptance evidence is established.
   A Tock pass, unaccepted checkpoint, handoff, low budget, or long execution does
   not justify completion. Report budget usage when the tool contract requires it.
5. Use blocked status only under the active tool's exact rules, including any
   repeated-blocker threshold. Difficulty, unchanged waits, or missing optional
   telemetry are not blockers. User pause/cancel and budget controls belong to
   the platform; do not fake them by marking complete or blocked.

Goal availability never changes scope, permissions, reviewer independence, or
the latest user's direction. If no goal tool exists, use the same continuation
and stopping decision with the existing package record; do not build a substitute
scheduler or promise automatic resumption that the platform does not provide.
